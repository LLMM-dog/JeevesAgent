# 提交信息规范

## 核心原则

提交信息回答的是**为什么改**，不是**改了什么**。改了什么看 diff 就知道，
为什么改只有当时的人知道。

反例（复述 diff，没有信息量）：

```
修改 loader.py，添加 parse_frontmatter 函数
```

正例（说清动机和后果）：

```
frontmatter 解析改用 yaml.safe_load

手写正则不支持块标量，而 `description: >-` 是 YAML 里描述多行文本的
常见写法。用正则解析时它会被当成字面值 ">-" 存进去，于是系统提示词里
这个技能的描述就是两个字符。
```

## 格式

```
<一句话摘要，不超过 50 字，不加句号>

<空行>

<正文：为什么要改、不改会怎样、有什么权衡>
```

## 摘要行

- 用陈述句，不用"修复了"这种完成时
- 不写"fix:"、"feat:" 这类前缀 —— 本项目不用 conventional commits
- 一次提交只做一件事。摘要行需要用"和"连接时，说明该拆成两个提交

## 正文该写什么

优先级从高到低：

1. **这个改动解决的具体问题**（最好有可复现的症状）
2. **为什么选这个方案**（如果有其它可行方案）
3. **踩过的坑**（尤其是"看起来该这样做但不行"的）
4. **已知的遗留问题**

## 不该写什么

- 不复述代码。`添加了 X 函数` 这类内容 diff 里有
- 不写"优化了性能"这种没有数字的说法。要写就给数据
- 不写"根据 review 意见修改" —— 写清具体改了什么行为

## 从 diff 提炼动机的方法

看 diff 时问自己三个问题：

1. 这段代码原来是什么行为？改完是什么行为？
2. 什么情况下会触发原来的行为，用户会看到什么症状？
3. 如果只是重命名或格式调整，那就直接说是重构，不要编造动机

参考 `references/examples.md` 有本项目历史提交的完整正反例对照。
