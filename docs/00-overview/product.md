# 产品定位

## 一句话

给单个开发者用的本地 Agent 工作台：浏览器里聊天、写代码、管任务，能力靠技能包和 MCP 扩展，代码在沙箱里跑，全部数据留在本机。

## 目标用户

只有一个人 —— 项目作者自己。这不是妥协，是设计前提。它直接决定了一系列取舍：

| 因为只有一个用户 | 所以不做 |
| --- | --- |
| 不存在越权 | 多租户、`owner_id` 分流、RBAC |
| 不存在并发争抢 | Redis 分布式锁、消息队列 |
| 不需要横向扩容 | 无状态化、外部 session store |
| 不需要计费 | 计量、定价、支付 |
| 只在本机访问 | 登录、JWT、refresh rotation、token 黑名单 |
| 数据量以千条计 | PostgreSQL、Elasticsearch、独立向量库 |

省下来的复杂度全部投到 agent 内核、工具生态和交互体验上。

## 核心场景

按优先级排序，路线图按此展开。

1. **写代码。** 读写本地文件、执行命令、跑测试、看报错改代码。这是最高频场景。
2. **任务管理。** 多步任务的 Todo 看板，AI 自己拆解、自己勾掉，人做验收。
3. **日常问答与检索。** 联网搜索、读网页、读本地文档、看图。
4. **重复流程固化。** 把稳定的工作流写成技能包或宏，下次一句话触发。

## 不做什么

明确划在范围外，避免范围蔓延：

- **不做知识库 / RAG。** 个人项目里，"把文件引用进对话"比"建索引再检索"更直接也更准。真需要时用 MCP 接外部服务。
- **不做多智能体编排 UI。** SubAgent 只作为工具存在（一个工具调用 = 一个独立子会话），不做可视化任务流编辑器。
- **不做插件市场。** 技能包直接放目录里，用 git 管。
- **不做移动端 / 桌面端打包。** 浏览器访问 `localhost` 就够。Electron 打包留到很后面再议。
- **不做团队协作。** 见上表。

## 形态决策

三个关键决策及理由：

### 1. Web UI（FastAPI + React/Vite），不做 TUI

TUI 启动快、适合纯写代码，但这个项目要的 Todo 看板、技能管理面板、图片预览、气泡树可视化、上下文占用条在终端里都会打折。

代价是要维护前后端两套。用全栈 snake_case 消除数据对齐成本来对冲。

### 2. 沙箱可插拔：本地子进程 + Docker 双后端，默认本地

只做 Docker 隔离的话隔离性好，但强依赖 Docker Desktop、首次启动要拉镜像，个人机器上偏重。只做本地执行 + 人工审批则轻，但不隔离。

这里定义统一的 `Sandbox` 接口，两个实现：

- `LocalSandbox`：子进程 + 工作区路径限制 + 超时 + 输出截断 + 审批模式。**默认**，零依赖。
- `DockerSandbox`：容器内执行，真隔离。**可选**，检测不到 Docker 时自动降级到本地并明确告知。

不装 Docker 也能全功能使用，装了就能开真沙箱。

### 3. SQLite + SQLAlchemy + Alembic，技能与人设走文件系统

结构化数据（会话、消息、Todo、模型配置、运行追踪）进 SQLite —— 需要按会话查、按序排、事务写，用 YAML 会在消息量上千后难受。

技能包、人设（`SOUL.md` / `USER.md` / `AGENTS.md`）、MCP 配置走文件系统 —— 需要手改、需要 git diff、需要直接从别处 copy 进来。存表的做法在个人项目里反而别扭 —— 手改要走接口、看 diff 要查库。

向量检索（如果真要做）用 `sqlite-vec`，不引独立向量库。
