# 定时任务

到点自动开一个新会话，把预设消息发给助手，跑完整的 agent 循环。

## 为什么值得做

用户不在电脑前时，agent 什么都做不了。而很多需求天然是周期性的：每天下班前总结改了什么、每周一整理待办、每小时检查某个服务的状态。

少见实现做了这个能力（676 行的 `CronTaskManager`）。它的调度结构值得抄，但有四个问题 ——。

## 两张表

| 表 | 内容 |
| --- | --- |
| `cron_task` | 任务定义：cron 表达式、时区、要发的消息、错过策略 |
| `cron_run` | 执行历史：计划时间、实际时间、状态、**关联的 session_id** |

执行历史必须落库 —— 定时任务是**无人值守**的，出问题时唯一的线索就是历史记录。 只用 `logger.write_log` 写文件，查起来要翻日志且没有"这次触发对应哪个会话"的关联。

关联 session_id 让用户能点进去看 agent 到底做了什么。没有它的话，会话列表里会莫名多出一个他没发起过的对话。

## 调度结构

抄 两个设计：

**最小堆 + 版本号懒删除**。改任务或取消任务时只 bump 版本号，不去堆里找那条记录删。worker 弹出堆顶后对账，版本不符就跳过。

理由：`heapq` 没有 O(log n) 的删除，要删中间某条只能重建整个堆。而任务的增删改在管理界面上是频繁操作。

**Event + wait_for 的可中断等待**。不能用 `asyncio.sleep(timeout)` —— sleep 6 小时期间新增一个"1 分钟后执行"的任务，那个新任务要等 6 小时后才被看到。

### 执行必须并发

```python
self._spawn(task_id, when)                              # create_task
self._schedule_next(task_id, cron, tz, base_ms=when)    # 立刻排下一次
```

一次任务触发的是一轮完整的 agent 对话，可能跑几分钟。 直接 `await`—— 两个都设在 9:00 的任务，第一个跑 5 分钟第二个就 9:05 才执行；第一个卡住的话后面**所有**任务永久不执行。

并发上限是 3。不限的话一个"每分钟"的任务配上慢对话会不断堆积，把 LLM 配额和内存吃光。

`create_task` 之后异常必须在任务内部吞掉 —— 逃出去会变成 unhandled task exception，只在 GC 时打一条警告，而 `cron_run` 那条记录永远停在 `running`。

**下一次触发要在执行之前排**：放在执行之后的话，跑五分钟的任务会让下次触发也推迟五分钟，而 cron 的语义是按绝对时间触发。

## 错过的窗口

任务设在每天 9:00，进程 8:50 挂了、9:30 才重启 —— 这次触发怎么办？

 重启后从数据库重算 `exec_time`（croniter 取"下一个"），所以 9:00 那次**完全消失且无任何记录**。用户视角是"我的日报今天没发"，而没有线索指向"服务当时没在跑"。

这里靠 `last_fired_at` 检测：

```python
prev_ms = sch.to_ms(sch.prev_before(t.cron, t.timezone))
if prev_ms > t.last_fired_at:
    # 在服务没运行的那段时间里错过了
```

两种策略，per-task 配置：

| 策略 | 行为 |
| --- | --- |
| `skip`（默认） | 不执行，但在历史里记一条 `missed` |
| `run_once` | 启动后立刻补跑一次 |

默认 skip 而不是补偿：服务停了三天的话，补偿逻辑一不小心就变成触发 72 次（每小时的任务）。而且昨天的日报今天补出来意义不大。

补偿有 6 小时的时间窗，超过就只记录。

**无论哪种策略都要落一条记录** —— 静默是最糟的选择。

处理过的窗口要更新 `last_fired_at`，否则同一个错过窗口会在每次重启时重复产生记录。

## 时区

全部用 tz-aware datetime，任务表存 IANA 时区名。

naive datetime 在 DST 切换日会出错：春季跳过的那小时任务不触发，秋季重复的那小时触发两次。 全程 naive（全文搜 `tz`/`timezone`/`astimezone` 零命中）。

Windows 上需要 `tzdata` 依赖 —— 缺了的话 `ZoneInfo` 抛异常，而容错逻辑会静默回落本地时区，**所有时区变成同一个**。

## 不做 `execute` 字段

任务有个 `execute` 字段，存一段 Python 代码，用 `exec()` 加完整 `__builtins__` 在 agent 进程里跑 —— `import os; os.system(...)` 完全可用。

它比 `run_python` 更危险：`run_python` 的代码是模型当场生成、用户在审批框里能看到；`execute` 是**存在库里的**，创建时看一眼，之后每天自动跑，**没有任何审批环节**。

需要"先取数据再分析"的话，让 agent 自己在对话里调 `run_shell` / `web_fetch` —— 那些已经过沙箱和审批。

不做这个字段还顺带避免了 另一个问题：它用 `redirect_stdout` 捕获输出，而那改的是**进程全局**的 `sys.stdout`。当前串行执行碰巧没事，一旦改成并发就会串台。

## 无头执行

```python
prep = await chat_service.prepare(session_id=sid, content=prompt)
async for _chunk in chat_service.stream(prep):
    pass        # 【必须完整抽干】
```

`stream()` 是 async 生成器 —— 没有消费者的话函数体根本不会执行。副作用（消息落库、工具执行、追踪）都在生成器内部发生。

这里有一条硬性要求：绝不能走"等外部连接来触发执行"的路。定时任务是最典型的无头场景 —— 触发时用户可能根本没打开浏览器。

### 强制 auto 审批

任务触发的会话强制 `approval_mode = "auto"`。

`manual` 模式下 agent 会停下来等审批，而**没有人在旁边点** —— 任务会挂到审批超时（5 分钟）然后失败。

这意味着定时任务里的 agent 能不经确认执行命令。**这个风险在创建界面上有显眼提示**，不埋在文档里。

## 容器清理

Docker 后端是每会话一个容器，而定时任务**每次触发都建一个新会话** —— 不清的话每次触发泄漏一个容器。

实测模拟三次触发就留下三个常驻容器。一个"每小时"的任务跑一天是 24 个，不重启就没有上界。而普通会话有删除入口（用户手动删会话时清理），定时任务的会话用户没有动力去删。

所以两处都做：任务在 `finally` 里清自己的会话，外加调度器起一个独立的周期扫描（`SWEEP_INTERVAL`，5 分钟）调 `cleanup_expired()`。

扫描不能挂在 cron 的 `_tick` 里 —— 那个循环只在任务到点时才醒，没有定时任务的用户永远不会触发回收。

## 删除与停用要取消正在执行的那次

删任务或停用任务时，正在跑的 asyncio task **不会自动停** —— agent 对话会继续跑完，继续烧配额、继续执行工具。用户点了"删除"却发现助手还在动。

删除的顺序必须是**先取消再删**：反过来的话那次执行的 `finally` 会去写 `cron_run`，而 task 行已经没了（CASCADE 把 running 记录也删了），于是 `finish_run` 走补记录分支撞外键，`IntegrityError` 被两层 suppress 静默吞掉 —— 表现是对话跑完了但账面上什么都没发生。

`repo.finish_run` 现在也会先确认任务还在，作为双保险。

## 停用再启用不补跑

PATCH 启用时会把 `last_fired_at` 刷到现在。

不刷的话错过检测会认为停用期间的窗口都错过了 —— 落一条 missed 记录，或者（`on_missed=run_once` 且在宽限内）**立刻补跑一次**。用户只是关了又开，却看到任务自己跑了。

## 单实例假设

调度器是模块级单例，本项目**假设单实例部署**。

多实例下两个调度器会各自触发同一个任务。真正解决需要数据库层面抢锁（`UPDATE ... WHERE last_fired_at < ?`），那是分布式调度的复杂度，个人项目不需要。

但这个假设必须写清楚 —— 否则将来有人部署两份会发现任务重复执行（"日报发了两份"），而完全找不到原因。启动脚本的端口占用检查顺带保证了这一点。

## 启动时的清理

`cron_run` 里遗留的 `running` 记录要标成失败。

进程被 kill -9 时那些记录永远停在 `running`，用户看到"任务卡在执行中"且分不清是真在跑还是上次没退干净。

这和 Docker 沙箱的遗留容器清理、启动脚本的端口检查是同一类问题：**依赖退出钩子做的清理，入口处都要能兜住**。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/cron/tasks` | 列表，含调度器状态 |
| POST | `/api/cron/tasks` | 新建。**入口校验 cron 表达式和时区** |
| PATCH | `/api/cron/tasks/{id}` | 修改，改完自动 reload 调度器 |
| DELETE | `/api/cron/tasks/{id}` | 删除 |
| GET | `/api/cron/tasks/{id}/runs` | 执行历史 |
| POST | `/api/cron/tasks/{id}/run` | 手动触发一次 |
| POST | `/api/cron/validate` | 校验并预览接下来 5 次触发时间 |

**入口校验**很重要： 只在调度时 catch `CroniterBadCronError`，所以非法表达式能存进库，然后每次调度都抛异常，而用户以为任务建好了。

错误信息要具体到"哪里不对"：

```
cron 表达式应有 5 段（分 时 日 月 周），收到 4 段：'0 9 * *'。
例如每天 9:00 是 "0 9 * * *"
```

**手动触发**是为了缩短调试反馈周期 —— 建一个"每天 9:00"的任务，不然要等到明天才知道 prompt 写得对不对。

**预览**是因为 cron 表达式很容易写错且错得不明显：`0 9 * * 1` 到底是周一还是周日？看到"接下来三次是 8/10 09:00、8/17 09:00、8/24 09:00"就一目了然。
