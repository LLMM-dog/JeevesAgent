# 语音输入

点麦克风说话，识别出的文字插到输入框光标处。

## 为什么用浏览器 API 而不是本地 whisper

零依赖、零配置。`SpeechRecognition` 是浏览器内置的，不需要装模型、不需要 ffmpeg、不需要额外的转写接口。

本地 whisper 准确率更高（尤其是中英混说、专业术语），但要拉几百 MB 模型 + 装 ffmpeg + 写一个转写端点 —— 对"个人项目模板"来说太重了。

代价是**音频会离开本机**，见下面一节。

## 常见实现

只有  有。它做对了三件事，照抄：

| 做法 | 为什么 |
| --- | --- |
| 200ms 长按延迟才启动 | 轻触不该触发录音 |
| 识别结果插在**光标处** | 用户可能是在已有文字中间补一段 |
| `onend` 和 `onerror` 都重置状态 | 服务可能自己断开，此时没有 onerror |

但它有几个缺口：

**不支持时只 `console.warn` 然后 return，按钮还在界面上。** 用户点了没反应，也不知道为什么。而 `SpeechRecognition` 至今不是 Baseline —— Firefox 长期不支持。

**权限被拒后是空处理**（相关实现 一个空的 if 分支）。用户不知道要去哪里改。

**`lang` 硬编码 `zh-CN`。** 说英文会被强行识别成谐音的中文词，而用户完全看不出是语言设置的问题。

**没有音频上传的提示。**

## 三个关键决定

### 一、不支持时整个不渲染入口

```tsx
{speech.supported && !busy && (
  <button ...>
```

和"选图按钮只在视觉模式下出现"是同一个原则：**给一个能点但没用的按钮只会让人困惑**。

这条断言看起来很小，但它是这个功能唯一的降级逻辑，而且**在 Chrome 上完全看不出来坏没坏** —— 大部分开发都在 Chrome 上。所以专门有测试盯着它。

### 二、错误码翻成能指导下一步的中文

原始错误码是 `not-allowed` / `no-speech` 这种，直接显示等于没说。而这几种失败的**处理动作完全不同**：

| 错误码 | 提示 |
| --- | --- |
| `not-allowed` | 点地址栏左侧的图标重新允许，然后刷新页面 |
| `no-speech` | 检查麦克风是否被静音或选错了设备 |
| `audio-capture` | 可能被其它程序占用，或系统里没有可用输入设备 |
| `network` | Chrome 的语音识别需要联网（音频要发到 Google 的服务器） |
| `aborted` | 不提示 —— 这是用户自己取消的 |

`network` 那条最容易让人困惑：明明是"语音识别"，为什么报网络错误。所以提示里直接说明原因。

### 三、明确告知音频会上传

MDN 写得很清楚：Chrome 的实现是服务端识别，音频发到 web service，所以离线不能用。

按钮的 `title` 里直接写"音频会发到浏览器厂商的识别服务"。

**为什么一定要说**：这个项目其它地方（私密模式、无鉴权警示条、沙箱降级提示）都明确告知了数据流向。语音是唯一一个"**用户说的话直接离开本机**"的入口，不说反而更不一致。

`processLocally` 是新加的属性，支持的浏览器上可以要求本地识别。目前支持面很窄，所以默认按"会上传"提示 —— 检测到支持时才不提示。

注意 `private_mode`（不写长期记忆）和这件事**是两回事**：那个管的是数据落不落库，管不了音频往哪儿发。

## 其它实现细节

**回调放 ref 而不是 deps。** 父组件重渲染时 `onText` 必然是新函数，放进 `useCallback` 的 deps 会重建 recognition 实例，正在进行的识别被打断。

**`continuous = true`。** 说完一句不自动停，让用户自己控制结束。`false` 的话长句子要点好几次。

**必须要 `interimResults`。** 没有的话按下按钮后好几秒界面毫无反应，用户不知道到底有没有在听。临时文本显示在输入框上方，配 `aria-live="polite"` 让读屏软件也能跟上。

**从 `resultIndex` 开始遍历。** `continuous` 模式下 `results` 是累积的，从 0 遍历会把已经插入过的文本重复插一遍。

**重复 `start` 视为 toggle。** 不判断的话连点两次会创建两个实例，第一个变成孤儿且永不停止 —— 麦克风一直开着。

**卸载时 `abort()`。** 不停的话麦克风一直开着（浏览器标签上的红点不消失），而用户已经离开这个页面了 —— 他会以为程序在偷偷录音。

**光标位置在 `requestAnimationFrame` 里设。** 此刻 React 还没把新值写进 DOM，直接设 `selectionStart` 会被随后的重渲染覆盖回去。

## 没做的

**空格键长按。**  有，但它无条件 `preventDefault()` 空格 —— 页面上其它按钮的空格激活会全部失效，这是可访问性回退。要做得对需要判断焦点是否在可交互元素上，收益不值这个复杂度。

**本地 whisper。** 留作后续可选项。真要做的话应该是后端加一个转写端点 + 前端用 `MediaRecorder` 录音上传，和当前实现是并列的两条路而不是替换。

## 验证边界

单测覆盖了 25 个场景（能力探测、识别流程、错误映射、清理）+ 5 个渲染场景，全部用假的 `SpeechRecognition` 驱动 —— jsdom 里没有这个 API。

**这些测试证明的是逻辑分支对，不是"真实麦克风能用"。** 真实验证需要连一个能驱动 Chrome 的工具（本机的 opencli 浏览器扩展未连接），加上真实的麦克风授权。构建产物里确认了语音代码和错误文案都在，但端到端的"说一句话、文字进输入框"没有自动化验证过。
