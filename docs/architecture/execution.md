# 命令执行与审批

## 安全边界（先说清楚）

**本项目默认在宿主机上直接执行命令，没有沙箱。**

`run_shell` 能做的事没有上界：`curl | sh`、删库、把 SSH key 传出去。文件工具受路径白名单约束，但命令不受——白名单在这里帮不上忙。

真正的边界只有两个：

1. **人工确认**（默认，`approval_mode="manual"`）
2. **容器/OS 级隔离**（需要自己搭）

同类实现/security.md` 把这个道理讲得最透，其论点直接适用：

> A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary.

所以这里不做半吊子沙箱，也不宣称有沙箱。

**反面例子**：`run_python` 工具描述写着"在隔离环境中执行 Python 代码"，实现是同进程 `exec()`，而它的 `get_safe_builtins` 自己承认保留了 `__import__`——一行 `import os; os.system(...)` 就绕过了路径白名单。描述与能力不符比没有防护更危险。

处理不可信代码或无人值守时，请在容器/VM 里跑整个服务。

## 命令行为

### 每次调用是独立进程

`cd` 不跨调用保留。要切目录用 `cwd` 参数，或在一条命令里用 `;` 连接。工具描述里明确写了这一点——不写的话模型会先 `cd src` 再单独调一次 `ls`，然后困惑为什么看到的还是根目录。

### stdin 是关闭的

`stdin=DEVNULL`。等输入的命令立刻拿到 EOF，不会挂死。

少见实现做了这件事。 让子进程继承 stdin，于是 `read`、等 y/n 确认的 `apt install` 会一直阻塞到 600 秒超时。成本极低、收益明确的一条。

工具描述里告诉模型改用 `-y` / `--non-interactive`。

### 超时杀整棵进程树

| 平台 | 机制 |
| --- | --- |
| POSIX | `start_new_session=True` 建新进程组，`killpg(-pid, SIGKILL)` |
| Windows | `taskkill /F /T /PID`（没有进程组语义） |

只杀直接子进程是不够的：`npm run build` 会 fork 出 node，只杀 npm 会留下 node 继续占 CPU 和端口，下次执行报"端口被占用"。

相关实现 是 `process.kill()`——它执行的是 `docker exec`，杀掉客户端后容器内进程继续跑，是实际存在的资源泄漏。

两个平台的代码路径完全不同，所以**各有一个测试**，不能只测一边。

### 退出码保真

PowerShell 会把所有非零退出归一成 1，所以自动追加 `exit $LASTEXITCODE`。详。

失败时**输出和状态一起返回**，不是只给一句错误：

```
（命令的完整输出）

命令以退出码 7 结束
```

按同类实现的做法 命令工具完全忽略退出码，模型只能猜。

### 输出截断

行数与字节数**双限制**，先到先算：

```python
max_output_lines = 2_000
max_output_bytes = 50 * 1024
```

单一字符数阈值（ 用 32000 字符）在多字节内容下与真实 token 消耗脱节——32000 个中文字符接近 32000 token，同样字符数的英文只有 8000。

**保留尾部**，因为命令输出的关键信息在末尾（编译错误、测试结果、最终状态）。文件读取相反——那时头部才关键。

**完整输出边读边落盘**，路径写进结果给模型：

```
[输出过长，仅显示第 3754~4000 行（共 4000 行）。完整输出：data/tmp/jeeves_output_xxx.txt]
```

三个必须做对的细节，每个都踩过：

1. 落盘要在**读的时候**，不能在截断的时候——否则文件和内存一样残缺
2. `total_lines` 要算**真实总数**，不是留在内存里的行数
3. 落盘目录要在**路径白名单**里，否则模型读不了

详。

启动时清理 `data/tmp` 下超过 24h 的文件——一条产出几百 MB 输出的命令会留下同样大的文件，而它只在那一轮对话里有用。

### 环境变量剔除

变量名含 `KEY` / `TOKEN` / `SECRET` / `PASSWORD` / `CREDENTIAL` / `PRIVATE` 的一律不传给子进程。

防的场景很具体：用户为了方便在系统里设了 `OPENAI_API_KEY`，模型执行 `env` 把它打印出来——那就直接进了上下文、日志、摘要。

命中即删，不做精确匹配：宁可多删几个无关变量，也不要漏掉一个 Key。

本项目的 Key 存在加密的 DB 里、不走环境变量，所以这一层防的是用户自己的系统变量。

## run_python 为什么起子进程

不用同进程 `exec()`：

| | 同进程 exec | 子进程 |
| --- | --- | --- |
| 超时能杀 | 不能（`exec` 无法中断） | 能 |
| 崩溃影响 | 拖垮整个服务 | 只死那个进程 |
| 输出捕获 | 要劫持 `sys.stdout` | 天然隔离 |

代价是启动慢几十毫秒，换来行为可预测。

**写临时文件而不是 `python -c`**，三个理由：

1. `-c` 传长代码会撞命令行长度上限（Windows 约 8191 字符）
2. traceback 里能看到真实行号，`-c` 显示的是 `<string>`
3. 代码里的引号不用转义

用 `sys.executable` 而不是 PATH 上的 `python`——虚拟环境里 PATH 上的可能是系统解释器，那样 import 项目依赖会失败。

临时脚本在 `finally` 里清理，超时路径也要清。

## 审批

### 哪些工具需要审批

| 工具 | 审批 | 理由 |
| --- | --- | --- |
| `run_shell` / `run_python` | 是 | 能做的事没有上界 |
| `write_file` / `edit_file` | 是 | 覆盖用户文件不可逆 |
| `read_file` / `list_dir` / `glob` / `grep` | 否 | 只读工具弹框会让审批变成噪音，用户很快就全点通过 |

### 超时视为拒绝

```python
approval_timeout = 300
```

这是与 关键分歧。它无限等待（相关实现 是裸 `await future`），用户点了开始就去开会，回来发现界面卡在审批框上，中间几十分钟什么都没发生。

而超时视为**批准**更糟——用户离开电脑时不应该有命令自己执行起来。

超时后告诉模型这不是用户主动拒绝：

> 操作未执行：等待用户确认超时（300 秒）。用户可能不在电脑前。如果这一步是必要的，可以先说明你要做什么并等用户回来确认。

### 拒绝理由要回给模型

```
用户拒绝了这次 run_shell 调用。不要重复同样的调用 —— 先问清用户的顾虑，或者换一种方式。
```

不说"不要重复"的话模型会原样重试。相关实现 是同样的做法。

### 模式切换必须立即生效

审批模式存在**模块级 dict**（`core/runtime_state.py`），不是 ContextVar。

`asyncio.create_task` 会复制当前 context，task 启动后外部对 ContextVar 的 `set()` 对它不可见。用户会遇到的症状是"我都切成自动了它还在弹框"。

 在 相关实现 为此留了注释，说明是同一个坑：

> 使用模块级 dict 而非 ContextVar，以便 WebSocket 主循环在处理 update_auto_approve 消息时写入的值能立即被正在运行的 Agent 任务中的工具函数读取到。

### 事件与前端

```
approval_required  { call_id, tool_name, args, timeout_at }
approval_resolved  { call_id, approved, reason? }
```

**`args` 必须完整**。只显示工具名等于让用户盲签——而盲签几次之后用户就会习惯性点通过，审批也就失去了意义。命令原文必须在眼前。

**`timeout_at` 是绝对时刻**而不是剩余秒数。事件到达前端有网络延迟，标签页在后台还会被节流；给剩余秒数的话前端得自己记事件到达时间，而那个时间本身就已经偏了。

**`approval_resolved` 不能省**。超时、取消、在别处批准这几种情况下，只发 required 会让弹窗永远留在界面上。

前端两个细节：

- **Esc 视为拒绝**。危险操作的默认选择必须是"不执行"。
- **确认按钮不设 autoFocus**。用户在输入框敲完回车的惯性会直接批准掉下一个弹窗。

### 取消时释放挂起的审批

用 `set_result(False)` 而非 `cancel()`：工具正在 `await` 这个 future，`set_result` 让它能正常返回"被拒绝"，而 `cancel` 会在工具内部抛 `CancelledError`，破坏工具自己的清理逻辑。

### 服务重启后的未决审批

Future 在进程内存，重启即全部丢失。常见实现是这样。

本项目也接受这个限制——重启后正在跑的 run 本身就没了，未决审批跟着丢是一致的行为。

## 常见实现的对比

| 维度 |  |  | 同类实现 | 本项目 |
| --- | --- | --- | --- | --- |
| 执行位置 | Docker 容器 | **同进程 exec** | 宿主子进程 | 宿主子进程 |
| 超时 | 硬编码 600s | 无 | 模型可选 | 模型可选，有上限 |
| 超时杀进程 | 只杀 docker 客户端 | — | 整棵树 | 整棵树 |
| stdin | 继承，可挂死 | — | ignore | DEVNULL |
| 截断 | 32000 字符 | **不截断** | 行/字节双限 | 行/字节双限 |
| 完整输出可取回 | 否 | 否 | 是 | 是 |
| 退出码 | **忽略** | — | 非零抛错 | 非零标错 |
| env 清理 | 无 | 无 | 只清自己的 | 按名字模式清 |
| 执行前审批 | **`pass` 空实现** | 有，**无超时** | 明确不做 | 有，超时视为拒绝 |
| 记住批准 | 无 | 会话级布尔 | 项目目录级 | 会话级 |

`block_for_permission` 函数体是一个 `pass`，命令工具也不调用它——基础设施写好了但没接上。
