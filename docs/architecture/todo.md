# Todo 系统

用户点名要的功能，参考 任务跟踪器。

## 定位

Todo 是**给用户看进度的**，不是给模型做规划的。

模型自己会规划（思维链里就在规划），Todo 的价值在于把这个规划**外化成用户可见、可验收的清单**。用户能看到"5 步里做完了 3 步"，而不是盯着一堆滚动的工具调用猜进度。

所以：Todo 的粒度应该是**用户关心的粒度**，不是每个工具调用一条。"实现登录接口"是一条，不是"读文件 / 写文件 / 跑测试"三条。

## 与 差异

任务跟踪器是"无状态"的（每轮重新生成，不落库），且另有一套接 Todoist 的工具。

本项目：

- **落库**（`todo` 表，见 [../architecture/schema.md](../architecture/schema.md#todo)）。会话关掉再打开进度还在。
- **不接 Todoist**。不引外部账号依赖。

## 数据模型要点

```
todo
  id            todo_xxx
  session_id    归属会话
  content       任务描述
  status        pending | in_progress | completed | cancelled
  priority      high | medium | low
  order_index   排序用整数
  created_at / updated_at
```

### 一个会话同时只能有一个 in_progress

这是**业务不变量**，靠应用层保证（SQLite 不做部分唯一索引）。

理由：如果允许多个 in_progress，"当前在做什么"就没有唯一答案，顶栏进度条不知道该显示哪一条。而串行执行的 agent 本来也只可能在做一件事。

`todo_write` 时校验：如果传入的列表里有多个 `in_progress`，只保留第一个，其余降为 `pending`，并在工具返回值里告知模型。**不报错** —— 这是模型的常见失误，纠正它比让它重试有效。

## 两个工具

### todo_write

**全量替换语义**：传入完整列表，覆盖该会话的全部 Todo。

```json
{
  "todos": [
    {"content": "读取现有登录逻辑", "status": "completed", "priority": "high"},
    {"content": "实现 JWT 签发", "status": "in_progress", "priority": "high"},
    {"content": "补单元测试", "status": "pending", "priority": "medium"}
  ]
}
```

**为什么用全量替换而不是增量操作（add/update/delete）**：

增量 API 需要模型记住每一条的 ID，而模型经常记错或幻觉出不存在的 ID，然后你得处理"更新一个不存在的 todo"这种情况。全量替换下模型只需重新输出完整列表 —— 它本来就把这个列表放在上下文里，重述一遍的成本远低于精确定位一条记录。

代价是每次写入的 payload 稍大。相比正确性可忽略。

实现上：按 `content` 匹配已有记录来保留 `id` 和 `created_at`（这样前端不会看到条目闪烁重建），匹配不到的视为新建。

### todo_read

读当前会话的清单。模型在长任务中途需要确认进度时用。

多数情况下模型不需要调它 —— 清单在上下文里。它的价值在压缩之后：压缩可能把之前的 `todo_write` 结果摘要掉，此时模型可以重新读一次。

## 工具描述怎么写

这是 Todo 能否被正确使用的关键。描述里必须说清**什么时候该用**：

```
在开始一个需要 3 步以上的任务时，先用 todo_write 列出计划。
每完成一步立即更新状态 —— 不要等全部做完才一次性标记。
只列用户关心的步骤，不要把每个文件读写都列成一条。
单条任务不要超过 20 个字。
```

"每完成一步立即更新"这条很重要。模型的默认倾向是做完所有事再总结，那样进度条就永远是 0% 然后突然 100%，等于没有。

## 前端呈现

### 顶栏进度条

```
[■■■□□] 3/5 · 工作中
```

常驻显示，点击展开看板。

状态文案：

| 情况 | 文案 |
| --- | --- |
| 有 in_progress | `工作中` |
| 全部 completed | `已完成` |
| 有 pending 无 in_progress | `待继续` |
| 有 cancelled | 计数里不算分母 |

### 看板

展开后按 `order_index` 排列，每条显示状态图标 + 内容 + 优先级色条。

用户可以：

- 手动勾选/取消勾选（会写库，模型下轮能看到）
- 手动删除某条
- 拖拽排序

**用户的手动修改对模型可见**。这是"人机协作"的具体体现：用户勾掉一条等于说"这个我自己做了"，模型下一轮读到就会跳过。

### 验收关闭

**全部完成后，进度条不自动消失，需要用户点击关闭。**

这个设计来自 ，是一个很好的细节：点击关闭 = 人工验收确认。自动消失的话用户可能根本没注意到任务已经"完成"了，也没机会检查完成得对不对。

关闭动作把该会话的所有 Todo 标记为已归档（不删除，仍可在历史里查）。

## 事件

`todo_updated` 事件，每次 `todo_write` 后发：

```json
{
  "items": [ ...完整列表... ],
  "stats": {"total": 5, "completed": 3, "in_progress": 1, "pending": 1}
}
```

发完整列表而非 diff。列表最多几十条，全量传的成本可忽略，而 diff 需要前端维护一致性状态 —— 一旦丢了一个事件就永久错位。

字段定义见 [../api/sse-events.md](../api/sse-events.md)。
