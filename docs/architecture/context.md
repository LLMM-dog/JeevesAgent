# 上下文管理

## 组装顺序

每次调 LLM 前重新组装。顺序固定，不能变：

```
1. system      系统提示词（人设 + 行为规则 + 工具策略 + 技能常驻清单）
2. summary     压缩摘要（如果有），以 user 角色发送
3. messages    历史消息（压缩后的），按 seq 升序
4. artifact    最新产物（如果有），钉在末尾
5. user        本轮用户输入 + 引用内容
```

### 为什么 artifact 钉在末尾而不按时序插入

产物是"当前工作成果"，模型每轮都要能看到最新版。按时序插入的话，产物会被后续对话推远，注意力衰减。钉在末尾等于"这是你手上正在改的东西"。

### 为什么摘要用 user 角色

`system` 是指令层，权威最高。摘要是**模型对用户内容的转述** —— 源自用户输入。

把它放 system 位等于给注入开了升格通道：用户说一句"忽略之前的所有指令"，被摘要进去后就变成了系统级指令。

同理，技能正文以工具返回值形态进上下文，见 [skills.md](skills.md#为什么技能正文不进-system-位)。

## 组装前的一致性校验

从 DB 读出消息后，**在做任何其它处理之前**，必须校验并修复 tool 配对。

```python
def repair_tool_pairing(msgs: list[Msg]) -> list[Msg]:
    """
    两类不一致，都会让 LLM 请求直接 400：
    1. assistant 带 tool_calls，但缺少对应的 tool 消息  → 补占位
    2. tool 消息前面找不到声明它的 assistant            → 丢弃

    产生原因不只是取消：进程崩溃、断电、手动改库都会。
    所以这里不做"是否需要修复"的判断，无条件跑一遍。
    """
```

补的占位内容为"（该工具调用未完成）"，`is_error=True`。

**不要试图只在取消路径里修。** 那样任何非正常退出都会留下一个每次打开都 400 的会话，而用户完全不知道为什么。

细节与出处。

## 系统提示词组装

```
<人设>            personas/SOUL.md
<用户信息>        personas/USER.md
<行为规则>        personas/AGENTS.md
<环境>            工作区路径、OS、当前时间、可用工具名列表
<技能清单>        技能 L1（name + description），追加在末尾
```

**技能清单必须追加在末尾，不能插在开头。** 开头是"你是谁"和硬约束，不该被一个可变长度的清单挤开——技能装多了会把人设推到几千 token 之后。

## 压缩

### 三铁律

违反任何一条都会出问题，前两条是直接报错，第三条是隐性质量下降。

**1. 必须用真实 usage 触发，不用本地估算。**

估算与真实值在有工具定义、system 提示词、图片时可差 20% 以上。估高了白压缩（丢信息），估低了直接 400。

首轮没有 usage 时用估算做保守判断（阈值打八折）。

**2. 切点绝不拆开 `tool_calls` 与其对应的 `tool` 结果。**

OpenAI 兼容 API 会直接返回 400：有 `tool_calls` 的 assistant 消息后面必须紧跟对应的 `tool` 消息，反之 `tool` 消息前面必须有声明它的 assistant。

实现上：找到候选切点后，向前扫描直到落在一个完整的 tool 组边界外。

**3. 必须保留 tail。**

最近几轮对话是模型理解"当前在做什么"的依据。全压缩掉之后模型会重新问"你想做什么"。

保留最近 `keep_tail_turns` 轮（默认 4 轮），这部分永不压缩。

### 触发阈值

```python
compact_trigger_ratio = 0.75  # 达到上下文窗口的 75% 触发
compact_target_ratio = 0.20   # 摘要目标长度：窗口的 20%
keep_tail_turns = 4           # 保留最近 4 轮
tail_budget_ratio = 0.4       # 但 tail 最多占窗口的 40%
compact_min_victims = 4       # 候选集少于 4 条不压（超窗口时例外）
estimate_safety_ratio = 0.8   # 走估算时阈值打八折
```

阈值用**比例**而非固定 token 数。因为模型窗口从 8K 到 1M 不等，固定值在小窗口模型上永不触发（直接 400），在大窗口模型上过早触发（白丢信息）。

窗口大小从 `model.context_window` 取，见 [providers.md](providers.md#上下文窗口)。

### 主动压缩

被动压缩的时机不由模型决定 —— 阈值只看总量，不知道"调研阶段已经结束、几十条工具输出已经没用了"。于是常见情形是：调研完还剩一半空间，等到 75% 触发时，正在进行的实现细节和早已无用的调研输出被一起压缩。

所以有 `compact_context` 工具，让模型在自然的段落边界上主动压。它只能**请求**压缩，实际执行仍走 `compaction.compact()` —— 那里有 head/tail 保留规则、artifact 钉住、摘要长度校验。让模型自己决定"删哪些消息"会绕过全部这些保护。

几个细节：

- 走 `urgent=True`，不看阈值。模型判断该压时上下文可能只用了 40%，走正常路径会直接返回什么都不做，而工具会报告"已压缩"—— 一个静默的谎
- 压缩后 `_last_prompt_tokens` 清零。不清的话下一轮会立刻再触发一次被动压缩
- 压缩后**重发一次 `context_usage`**。不发的话界面上的占用条还停在压缩前的数字，而用户刚看到"已压缩"的提示，两者矛盾
- 只在主 agent 注入回调（`depth == 0`）。子 agent 的上下文独立且短暂，压缩它等于白花一次 LLM 调用

### 摘要的长度预算按窗口算

```python
budget_tokens = max(200, int(model.context_window * compact_target_ratio))
budget_chars  = int(budget_tokens / 1.4)   # 中文约 1.4 token/字
```

这四个值（连同 `window_tokens` 和 `budget_percent`）都传进 `app/prompts/compact.md` 的占位符。

**不能写死字数。** 8K 窗口的模型和 128K 的差 16 倍：写死"压到 2000 字"的话，小窗口压完仍然超限（压了等于没压），大窗口则白丢信息（明明还有 100K 空间，却把细节砍光）。

**20% 只算对话部分**，不含系统提示词和工具定义。那两项是固定开销（本项目 16 个工具就 4300 token），算进额度的话 8K 窗口下摘要额度会被挤到几乎没有 —— 而那点长度装不下"用户约束 + 决定理由 + 失败原因"。

下限 200 token：配错成 1K 窗口时 20% 只有 200，宁可超预算也不要让摘要退化成一句话。

超预算只记日志**不截断**：摘要是结构化的（小标题分段），从中间切断会切掉最后一节，而"失败原因"完全可能排在末尾 —— 切掉它比超预算糟得多。也不重试：模型对 token 数没有精确控制力，第二次通常也压不到。

### tail 必须同时受轮次和 token 限制

这是实测撞出来的。只按轮次数会这样：

```
keep_tail_turns=4，每轮是 3000 token 的长回答
→ tail 自己 12000 token，而窗口只有 4200
→ 候选集被挤到只剩 3 条，min_victims=4 于是拒绝压缩
→ 上下文一路涨到窗口的 221% 才被上游 400 打断
```

日志里看到的是压缩**每轮触发、每轮放弃**：

```
compaction_triggered  used=7575 window=4200
compaction_skipped    reason=too_few_victims victims=3
```

所以 tail 取两个限制中更严的那个：轮次限制解决"保留几次交互"，token 限制解决"保留多少内容"。

另外两条配套的：

- **超窗口时 `urgent=True`**，忽略 `min_victims`。此时"压两条也比 400 好"。
- **最后一个 user 消息永不压缩**。压掉它模型就收不到当前诉求，只能猜或者反问"你想做什么"——比上下文超限更糟，因为超限有报错，这个没有。

### 真实 usage 要跨请求恢复

每个 HTTP 请求都新建一个 `AgentLoop`，`_last_prompt_tokens` 从 0 开始。不从库里恢复的话，**每次请求的第一轮都走估算分支**——而单轮对话（问一句、答一句、不调工具）恰好只有第一轮。于是"用真实 usage 触发"这条铁律在最常见的场景里根本没生效。

`load_context()` 里从最后一条带 `prompt_tokens` 的消息恢复。

### 压缩流程

```
1. 确定保留范围：system + 最近 keep_tail_turns 轮，再按 token 预算收紧
2. 候选集 = 全部消息 - 保留范围 - artifact - 已有 summary
3. 向前调整切点到 tool 组边界外
4. 用 compact 功能位的模型总结候选集
5. 校验摘要：占位符已替换、长度合理
6. 生成一条 role=summary 的消息
7. 新 messages = system + summary + tail + artifact（钉末尾）
8. 发 compacted 事件（带压缩前后 token 数）
9. summary 消息落库（原始消息不删，前端仍能看全部历史）
```

切点计算（第 1~3 步）是**纯函数** `plan_compaction`，不碰数据库也不调 LLM。切点错了的后果是上游 400，而这只在长会话里出现——开发时撞不到，上线后必然撞到。抽成纯函数才能穷举边界单独测。

### 摘要必须校验

实测踩过：占位符名字传错（`conversation=` vs 模板里的 `{{history}}`），`render` 找不到就原样留着，模型收到字面的 `{{history}}` 后回复"无对话历史内容"，**17 个字符替代了 9662 token 的历史**。

所有可观测信号都正常：压缩事件正常发出、token 数正常下降、日志无异常。只有摘要是垃圾，会话从此越来越糊涂。

两道检查：

```python
if "{{" in text:                    # 占位符没被替换
    return None
min_len = max(80, int(len(input) * 0.005))
if len(summary) < min_len:          # 压缩比超过 200:1 不可能是好摘要
    return None
```

单元测试抓不到这个——FakeLLM 直接返回预设摘要，不经过提示词渲染。**只有真实模型能暴露**，见 `scripts/verify_compact.py`。

### 真实模型的实测数据

`scripts/verify_compact.py` 把窗口登记成 4200 强制触发压缩：

```
压缩完成  12526 → 1817 tokens（省 86%），摘要 433 字
摘要里保留了 3/3 条早期约定
```

判定标准不是"模型答对了"——约定可能还留在 tail 里。而是**摘要正文里能不能找到那些约定**。

### compact 位不能配弱模型

这条容易搞错。直觉上压缩是"简单任务"，配个便宜模型省钱。但：

- `enrich` 类任务错一次只影响那一块内容
- **`compact` 错一次影响整个会话往后的全部推理** —— 摘要丢了关键约定，模型后面所有决策都基于错误的前提，而且不会报错

compact 位应该配和 chat 位同档或只低一档的模型。

## artifact

### 为什么需要专门的角色

这是用真实故障换来的设计，值得完整记录。

**如果产物当普通 assistant 消息存**：

1. 模型生成了一个 300 行的前端页面
2. 对话继续，上下文达到阈值，触发压缩
3. 压缩把那条消息摘要成"助手生成了一个登录页面"
4. 用户说"配色改深一点"
5. 模型手里**没有代码了**，只能照着摘要重写
6. **全程零报错**，用户只是觉得"怎么改完变样了"

**解法**：

- 产物存为 `role=artifact` 的消息
- 每个 `(session_id, agent_name)` 只保留**最新一版**（upsert，旧版本删除）
- 排除在压缩候选集之外
- 组装上下文时单独钉在末尾

### 什么算 artifact

由工具决定，不由模型决定。`write_file` 写出的完整文件、代码生成工具的输出算 artifact。零散的编辑（`edit_file`）不算。

`ToolResult.artifact_id` 非空即表示产生了 artifact。

## journal

`journal` 是 append-only 的完整流水，`messages` 是会被压缩重写的工作副本。

| | messages | journal |
| --- | --- | --- |
| 会被压缩重写 | 是 | **否，永不修改** |
| 发给 LLM | 是 | 否 |
| 落库依据 | 否 | **是** |

压缩只动 `messages`，绝不动 `journal`。所以数据库里存的永远是完整的原始对话，用户在前端能看到全部历史，即使模型自己已经"忘了"中段。

前端展示的是 journal（完整），模型看到的是 messages（压缩后）。这个分离是刻意的。

落库必须用外部传入的 `journal_sink` 而非 `state["journal"]`，原因见 [agent-loop.md](agent-loop.md#journal-sink)。

## 引用内容的注入

用户在输入框里引用的内容作为本轮 user 消息的一部分注入：

```
用户的实际输入文字

<引用 type="file" path="src/main.py">
文件内容...
</引用>

<引用 type="url" href="https://...">
网页正文 Markdown...
</引用>
```

**引用内容拼在用户文字之后**（`chat_service.py`：`m.content = f"{m.content}\n\n{res.text}"`）。

放前面的话模型先读到几十 KB 材料才看到问题，而"根据这些材料回答什么"是问题决定的 —— 先给问题再给材料，模型读材料时才知道自己在找什么。

图片引用在视觉模式下走多模态 content 数组，不走文本注入。

### 引用内容不落进 messages 的持久内容

引用的文件可能很大（几万 token）。如果把展开后的内容存进消息，会话历史会迅速膨胀，且下一轮压缩就会把它摘要掉（等于白引用）。

做法：数据库里 message 只存**引用清单**（type + path/href），展开的内容在每次组装上下文时**按需重新读取**。这样：

- 文件改了，下一轮自动看到新内容
- 历史记录小
- 压缩不会误伤

代价是每轮都要重读文件。本地文件读取成本可忽略。

## context_usage 事件

每次 LLM 调用后发 `context_usage`。字段清单以 [../api/sse-events.md](../api/sse-events.md#context_usage) 为准，这里只记设计理由。

前端显示一个占用条。用户能预判什么时候会压缩，从而决定是否该开新会话。

### 固定开销要单独报出来

用户发一句"你好"看到 4551 token，第一反应是"计数错了"—— 因为那句话只有 2 个 token。实际是 16 个工具的 JSON schema 占了 4298，系统提示词再占 1311，而这两项**每一轮都重发**。

不拆开的话用户唯一的解释就是"这个数字是错的"。拆开之后他能看到真正该动的地方（关掉用不到的 MCP、精简 AGENTS.md），而不是怀疑计数。

所以事件里带 `tools_tokens` / `system_tokens` / `tool_count`，前端分三段显示。

### 分项必须按比例分摊，不能直接相减

本地用 tiktoken(cl100k_base) 数，而模型用自己的分词器。实测本地数出 tools 4298 + system 1845 = 6143，而模型报的整个 prompt 才 4547 —— **本地高 35%**。

直接拿真实总数减本地分项的话，"对话内容"会变成 -1596。用户看到一个负数只会更确信这个计数是坏的，而我本来是想解释清楚它不是坏的。

所以本地的数只用来算**占比**，再乘到真实总数上。分项因此是近似值，前端要标出来。

### 百分比按窗口算，不是分项互比

三段的百分比分母都是 `window_tokens`。用"占已用部分的比例"的话，一个空会话里工具定义会显示成 70% —— 而用户要判断的是"还剩多少空间粘代码"，不是"工具在已用部分里占多大"。后者会让人误以为窗口快满了。

### 拿不到真实 usage 时也要发

有些中转站不返回 usage。那时回落到本地估算并标 `is_estimate=true`。

不发的话进度条会停在上一轮的值不动，用户以为卡住了。估算必须带上工具定义 —— 漏算会少报一千多 token，用户以为还很空。

### 发消息之前的固定开销

`GET /api/context-overhead` 单独返回工具定义和系统提示词的占用，不需要有 run 在跑。

新会话里没有任何 usage 事件，而固定开销此时已经确定了 —— 不显示的话占用条是空的，用户以为"还没开始用 token"。这个端点也按技能开关过滤，所以关掉一个技能之后数字会立刻变小。
