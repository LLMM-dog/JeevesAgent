# 创建一个宏

用户想把某段重复性工作流存下来。按下面的流程走。

## 第一步：先判断该不该做成宏

宏适合：

- 纯步骤指引，不需要跑脚本
- 流程稳定、会被反复用到
- 一篇 Markdown 能说清

不适合做成宏的（应该建议用户做成**技能**，即带 `scripts/` 的目录）：

- 需要执行代码、调用外部 API
- 需要大量参考文档支撑
- 内容超过 300 行

如果判断是后者，直接告诉用户"这个更适合做成技能"，并说明区别，不要硬塞成宏。

## 第二步：把流程问清楚

不要凭猜测写。至少确认这三件事：

1. **触发场景** —— 什么时候会用到它？这句话会变成 `description`
2. **具体步骤** —— 按顺序，每步做什么、产出什么
3. **边界** —— 哪些情况不适用、有什么前提

用户描述含糊时追问，不要自己补细节。写错的宏比没有宏更麻烦，因为它会被反复执行。

## 第三步：写文件

路径：`macros/<name>/MACRO.md`

`<name>` 用小写字母、数字、连字符。不要用中文或空格——它是目录名。

```markdown
---
name: <小写连字符名>
description: 当用户……时使用。<一句话说清适用场景>
version: 1.0
keywords: [关键词, 关键词]
---

# <标题>

## 适用场景

<什么时候用它，什么时候不用>

## 步骤

1. <第一步>
2. <第二步>

## 注意

<边界条件、前提、常见错误>
```

### description 决定这个宏有没有用

它是用户在提词器里看到的唯一信息。写**"什么时候用它"**，不要写"这是什么"。

反例：

```
description: Git 相关操作
```

用户看到这句话无法判断该不该选它。

正例：

```
description: 当需要把当前分支的改动整理成 PR 描述时使用。会先读 git log 再按模板产出。
```

## 第四步：写完确认

用 `write_file` 落盘后，告诉用户：

- 文件路径
- 下次输入 `!` 就能在列表里看到它
- 不需要重启

## 关于 ${MACRO_DIR}

宏正文里可以用 `${MACRO_DIR}` 引用宏自己所在的目录，它会在加载时被替换成
真实绝对路径。宏一般不需要附件，所以这个变量很少用到。
